# 22 Survivor Walkthrough 設計書

## 目的

被災者視点で **J-00 開始から再訪まで** を通し確認し、次の3つが満たされているか検証する。

1. **迷わない** — 何をすればいいか、どこを押せばいいかが分かる
2. **次が分かる** — 今やることが1つに見え、理由が理解できる
3. **前に進んでいる実感がある** — 初回・再訪・Recovery移行の各段階で進捗が伝わる

**今回の目的は機能追加ではなく、UX friction（つまずき）の発見である。**

Walkthrough は「綺麗に確認する」より **意地悪に見る** 方がよい。  
生活再建ナビの価値は「普通の人が迷わない」ことにあり、開発者が納得するより **疲弊した被災者が最後まで迷わず使えるか** を証明するフェーズに入っている。

**この段階では Cursor への追加実装依頼より、Case1 を通して friction を F-001 形式で残すことが優先。**

### 実施手順（Case1 最初の1本）

```
1. セッションリセット
   ↓
2. スマホ幅 375px
   ↓
3. Case1（宇城市・半壊想定）を最初から通す
   ↓
4. 本ドキュメントのチェック欄を埋める
   ↓
5. 違和感だけ F-001 形式で記録（改善案は書かない）
```

F-001〜F-010 程度集まった時点で、**即修正 / A-B検討 / 維持** を判断する。  
その時点の Cursor 指示は「作って」ではなく **「直すべき場所だけ直して」** が正解。

## 重点3ポイント（Case1 最初の1本）

Walkthrough 全体の中でも、特に以下3か所で **心が止まるか** を見る。

### ① 最初の10秒 — 離脱判定

| 確認 | メモ |
|------|------|
| 何のサービスか分かるか | |
| 「自分に関係ある」と感じるか | |
| 次に押すボタンが迷わないか | |

### ② J-00 終了直後 — 最重要

被災者はここで「結局、自分は何をすればいいの？」になりうる。

| 確認 | メモ |
|------|------|
| **現在地** が分かるか | |
| **次の一歩** が1つに見えるか | |
| **なぜそれをするか** が理解できるか | |
| 上記3つが **1画面でつながっている** か | |

### ③ Action 完了後〜再訪 — プロダクトの本当の価値

普通の情報サイトは「読んで終わり」。生活再建ナビは次が残ることが価値。

```
前回ここまでやった → 今ここ → 次これ
```

| 確認 | メモ |
|------|------|
| 前回の進捗が残っているか | |
| 今の状況が分かるか | |
| 次の一歩が残っているか | |
| 「終わったこと」と「次」が混ざっていないか | |

## 支援者同伴利用

災害後は本人が疲弊し、**家族・自治体職員・ボランティア** が横で一緒に操作する場面が多い。  
Walkthrough 時は、可能であれば **2人目の視点**（画面を見ているだけ）でも評価する。

| # | 確認項目 | OK / NG / メモ |
|---|----------|----------------|
| 1 | 本人以外が横で見ても、今何をしている画面か説明しやすいか | |
| 2 | 「次に一緒に確認すること」を一緒に読んで確認できるか | |
| 3 | 個人情報（詳細な家族構成・住所等）を出しすぎていないか | |
| 4 | 支援者向けの専門用語・行政内部用語が表に出ていないか | |
| 5 | 支援者が代わりにタップしても、本人のケースとして自然に進むか | |
| 6 | 「AIに任せっぱなし」ではなく「一緒に確認している」印象か | |

**位置づけ:** 将来的な行政・社協連携の下地だが、**今は被災者支援品質の確認** として扱う。  
About / 開発者情報（信頼形成レイヤー）とは別フェーズ（B 完了後 → A）。

## friction 記録フォーマット

Walkthrough 中は **観察ログ** として書く。改善案・結論は F-001〜F-010 集まってから。

### 簡易形式（Walkthrough 中に使う）

```markdown
### F-001

- **場所:** /start
- **分類:** 迷った | 固い | 安心した
- **状況:** 最初に「AIケースワーカー」と出てきて、相談相手なのかサービス名なのか一瞬迷った。
- **影響:** 低 | 低〜中 | 中 | 高
- **備考:** ボタン自体は分かる
```

**書かなくていいもの（この段階）:**

- 改善案（「〇〇を消すべき」等）
- 結論・優先度の確定
- 実装指示

同じ表現でも初回利用者 / 支援者同伴 / 年齢層で感じ方が違う。**どこで心が止まるか** のログ取りが目的。

### 詳細形式（F-001〜F-010 整理後）

改善判断に入る段階で、必要な項目だけ詳細化する。

```markdown
### F-001（整理後）

- **発見:** 最初の画面で何を押すかわからない
- **場所:** /start
- **Case / Phase:** Case1 / Phase1-1
- **問題:** CTA の意味が弱い
- **改善案:** 文言変更のみ
- **影響範囲:** 表示のみ / ロジック変更なし
- **優先度:** P1 | P2 | P3
- **判断:** 即修正 | A/B検討 | 維持
- **ステータス:** 未対応 / 対応中 / 完了
```

### 優先度定義

| 優先度 | 定義 | 例 |
|--------|------|-----|
| **P1** | 利用継続に影響 — ここで離脱する | J-00 途中で詰まる、完了ボタンが見つからない |
| **P2** | 理解に影響 — 進めるが不安・誤解が残る | なぜこの Action か分からない、Recovery 移行の意味不明 |
| **P3** | 改善余地 — 体験は成立するが磨ける | 文言のトーン、折りたたみの位置 |

### 改善時の原則

1. **P1 から対応** — 1 friction あたり最小 diff
2. **表示・コピー優先** — ロジック変更は原則しない
3. **ヒーローカードを汚さない** — About・説明・補助情報は別導線
4. 対応後、該当 Phase を **再 Walkthrough** して回帰確認

## friction 仕分け（Walkthrough 後）

F-001 以降のメモを以下に分類する。**今はコードを増やすより、この判定の精度を上げる段階。**

| 分類 | 判断 |
|------|------|
| **P1** | すぐ修正 — 迷う / 不安 / 信用できない（被災者視点） |
| **P2** | B 完了前に検討 — 理解に影響、コピー or 軽い UI で済みうる |
| **P3** | A フェーズ以降 — 信頼形成・About・表現の磨き |
| **対象外** | 触らない — 開発者嗜好のみ、現状で体験は成立 |

### 修正判断 — 4つの問い（必ず通す）

[24 プロダクト表現方針](./24_プロダクト表現方針.md) § 修正判断4つの問い

| # | 問い |
|---|------|
| 1 | これは被災者の **不安を減らす** か？ |
| 2 | **迷いや負担を減らす** か？ |
| 3 | **信頼につながる** か？ |
| 4 | **開発者側の都合** になっていないか？ |

### B と A の境界（F-001 仕分け時）

| B（今直す） | A（後で信頼形成レイヤー） |
|------------|-------------------------|
| ボタン位置が分からない | 誰が作っているのか気になる |
| 表現が冷たい | 情報源への不安 |
| 情報量が多い | 応援したい |
| 次に何を押すか迷う | 意見を届けたい |

F-001 整理時は **P1〜P3** と **コピー修正だけで済むか / UI 変更が必要か** も併記する。

### Walkthrough の重点（機能確認より）

一人で使った時に **孤独感や不安が増えないか** を見る。

```

4. P3 → A フェーズ（信頼形成レイヤー）と一緒に検討
```

| 順序 | 内容 |
